An AI agent can self-activate a privileged Entra role. No human, no MFA.

Darius Frank · November 2026

Entra Agent ID gives AI agents real identities. One kind, the agent user, is built on the user object and gets a token that says idtyp=user, so to most of Microsoft 365 it looks like a person.

Microsoft says agent users can't hold privileged admin roles. Semperis showed that in practice you can still assign three of them: Global Reader, Security Reader, AI Administrator. That was a standing grant. I wanted to know if an agent user could turn on an eligible one by itself.

Eligible is the PIM model. You don't hold the role, you activate it when you need it, and activation is where the guardrails sit: justification, MFA, approval. For a person that's the safe setting. An agent can't do MFA and has no human driving it, so the question was whether it can finish that activation at all.

I ran it in my own tenant

I made a test agent user eligible for Global Reader. Its activation policy was on the Entra default, which asks for a justification string and nothing else. MFA and approval are off by default. I gave the agent user the one scope PIM needs to activate a role, minted the agent user's token through the blueprint flow, and had the agent call selfActivate on Global Reader with its own token.

It came back Provisioned. No human, no MFA. The agent turned on a privileged role for itself, and the role shows up in the token afterward. By every signal PIM reports, it worked.

Why that matters for auditing agents

An audit that only reads active role assignments calls this agent user clean. The eligible role lives at a different endpoint, and the agent can switch it on any time. If you let agent users hold eligible privileged roles, reading active assignments is not enough.

Maester check · MT.1210

This is the gap behind a check I added to Maester, the open-source Entra and M365 security test framework. MT.1210 reads eligible role assignments on agent users, not just active ones, so an agent user that is one activation away from a privileged role is flagged. Merged into maester365/maester.

Then I checked if the role actually did anything

I stripped the agent user's access back to only the scope needed to activate, so nothing on the token could read directory data on its own. Role off: the agent tried to list users and was denied, as expected. The agent activated Global Reader. Role on, with Global Reader confirmed in the token: the same read was still denied.

So the activation is real in PIM and inert for the agent-user token. Entra accepts it, writes the role into the token, reports success, and the role grants no working access. The reads that earlier looked like the role working were the token's own scope doing it.

What to do about it

Check eligible assignments on your agent users, not just active ones. PIM will report a self-activation as Provisioned whether or not the role ends up usable. And the one control that stops the self-activation is one an agent can't meet: require MFA or a Conditional Access authentication context on activation. An agent user can't satisfy either, so that requirement blocks it cleanly.

One thing to be clear about: inert is how it behaves today. That's Microsoft's current implementation, not a promise. An eligible privileged role sitting on an agent is a standing grant, and the day the token behavior changes it resolves to real access. You want to see it in an audit now, not after.

The inert part I can't fully explain. An activation that succeeds everywhere PIM reports but delivers no access looks like a gap on Microsoft's side. If anyone's dug into why, I'd be interested to hear it.
